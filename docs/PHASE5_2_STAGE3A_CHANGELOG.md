## 3A-1 Dataset layer (`dewako/backtesting/datasets.py`)
Built on the existing point-in-time `CandleStore` and backfill (no duplicate of either). A dataset is validated, hashed and frozen, or refused.

- **Refused (ERROR):** empty range; naive time; off-grid, out-of-range, duplicate or out-of-order candles; non-finite or non-positive price; non-finite or negative volume; high/low that do not bound open/close; any missing candle not explained by the caller (reported as runs with position and length); an "explained" gap that actually exists; a close-to-close jump or in-candle range above `spike_limit` (default 10 %) unless that exact candle is acknowledged.
- **Recorded (INFO):** explained gaps, zero-volume candles, candles using a revision published before `as_of`, candles with confidence below 1.0.
- **Identity:** `content_hash` = SHA-256 over symbol, timeframe, source and every value of every candle (floats as exact hex), order-independent. `Dataset.record()` is what a run record will store (hash, source, range, `as_of`, counts, explained gaps, acknowledged spikes, finding summary).
- **Point in time:** data is read as known at `as_of` (default: end of range). A correction published after `as_of` cannot change an old dataset; unclosed candles are excluded.
- **Provider-agnostic:** the source is a name in the store. Exchange adapters added in a later phase fill the same store; nothing here changes.
- **Tests:** `tests/test_stage3a_datasets.py`, 22 tests. Mutation checks, each fails at least one test (code restored, bytecode caching disabled): off-grid, duplicate, order, OHLC, non-positive price, volume, every-gap-explained, spikes never refused, acknowledgement ignored, close-to-close check, explained-but-present, hash identity / high / volume / open / time / input-order, `as_of` ignored, rejection removed. Two hash mutations (high, volume) first SURVIVED; `test_every_field_of_every_candle_is_part_of_the_hash` was added. One earlier mutation run was invalid (stale bytecode and a pipeline that killed the restore) and was rerun cleanly.
- **Findings while testing:** the store already refuses NaN (NOT NULL), so NaN is tested on raw lists; a spike produces two suspect candles (the jump and the jump back), and both must be acknowledged.
- **Limits:** the spike limit is a heuristic, 10 % may be wrong for a calm instrument or a volatile 1m crypto candle (adjustable per call); gap explanations are supplied by a human and are not verified against exchange calendars; real downloads from public providers were not run here (no network to exchanges); the validation does not detect plausible but wrong values.
- **Evidence (local):** SQLite 610 passed, 39 skipped (36 HTTP tests need fastapi, 3 PostgreSQL-only); PG16 613 passed, 36 skipped (the same HTTP tests); ruff real-error check clean. Hosted CI run 41938811121 on `a7578ea`: all jobs green.

## 3A-2 Simulated exchange adapter (`dewako/backtesting/sim_adapter.py`, `clock.py`)
A `SimulatedExchange(ExchangeAdapter)` (name `sim`, environment PAPER, `SIMULATED=True`) driven by a `VirtualClock`. It never contacts anything; there are no credentials.

- **Modelled (pessimistic by default):** bid/ask around the mid with a half-spread that widens with the bar range; slippage = base + range term + size/volume impact; fee on every fill; a per-bar participation cap shared by all waiting orders (older orders first), partial fills over later bars; latency (an order fills at the price when it arrives); step/min/max quantity and min-notional rules (rounded down, never up); balance and holdings checks (no shorting); MARKET orders only; repeated client id = same order; cancel keeps what was filled; gaps fill at the gapped quote, not at the stop price.
- **Faults (deterministic):** maintenance windows (reject), seeded reject rate (SHA-256 of seed and client id, repeatable), outage windows (`ConnectionError` on every call), lost-response windows (order accepted, `TimeoutError` raised). Test with the real `ExecutionEngine`: an outage blocks with nothing sent; a lost response becomes OUTCOME_UNKNOWN and is reconciled from the exchange, one order, one fill, never sold twice.
- **Tests:** `tests/test_stage3a_sim_adapter.py`, 29 tests. 22 mutations checked; 3 first SURVIVED (range slippage ignored, newest-order-first, min-qty ignored) because the existing tests were dominated by other effects or filled orders on creation. Added: range-slippage-only test (spread, base and impact set to zero), a latency-queued order-priority test, and `min_notional` lowered so the min-qty rule is what rejects. All three now fail the suite; code restored and compared.
- **Finding for 3A-3:** persistence `now_iso()` uses the wall clock (orders, positions, audit, exit tracking) while engine/monitor accept `clock=`. Replay must make the persistence time source injectable or time-stop ages and stall detection will use real time.
- **Limits:** the cost model is a conservative assumption, not calibrated to a real exchange; no limit/stop orders on the venue (stops are enforced by the engine/monitor as in production); no order book depth, no funding or borrow.
- **Evidence (local):** SQLite 639 passed, 39 skipped; PG16 642 passed, 36 skipped; ruff real-error check clean. Hosted CI run 41972742718 on `0551451`: all jobs green.

## 3A-3 Replay harness (`dewako/backtesting/replay.py`, `dewako/core/timesource.py`)
Replays a validated `Dataset` through the REAL pipeline (Strategy → Signal → Risk Engine → Execution Engine → `SimulatedExchange`; Exit Monitor for stop, take-profit and time stop) in a throwaway SQLite database. No trading logic is re-implemented. Results are marked `simulated=True`; the only adapter is the simulated one.

- **Injectable time (production change, behaviour identical by default):** new `core/timesource.py`. `db.now_iso`, `types.utcnow`, the safety controller's three clock reads and the engine's recovery cutoff now ask it for the time. Nothing overrides it in the application (a test greps the whole app for `virtual_time`, `replay`, `sim_adapter`). `virtual_time` cannot nest and refuses naive datetimes; it is switched on before the database is created, so even migration stamps are simulated. A test scans every timestamp-looking value in every table: none is wall-clock.
- **Timing rules (all pessimistic):** the strategy sees only closed candles; it decides when a bar closes and its order fills at the NEXT bar's open plus costs. Inside a bar the path is open → low → high → close, with an extra price point where a stop or take-profit level is crossed (placed in bid terms, as the monitor tests the bid), so exits fill near the level plus costs, not at the bar extreme; a gap fills at the gapped quote; a bar that could hit both stops out first.
- **Equity** is marked at the bid after each bar close and recorded in the risk state exactly as the runtime does.
- **Explicit quote-guard limits:** the runtime refuses to trade without them (first run was BLOCKED: "quote guard configuration is missing"), so `ReplayConfig` carries its own (0.5 % spread, 2 % deviation, 30 s age) and records them with the run.
- **Loud failures:** an unknown strategy used to produce an all-ERROR run that looked like "no trades" (BotRunner swallows exceptions); it now raises up front. An exit whose reason is unknown is labelled `UNKNOWN`, not `STRATEGY`.
- **Tests:** `tests/test_stage3a_replay.py`, 21 tests (+23 subtests: every registered strategy replays 219 ticks with no ERROR tick and no incident). 24 mutations checked on replay/timesource. Survivors found and fixed by tests: resting-order sync (new split-entry test), recorded equity (risk-state test), exit-reason fallback masked the label (fallback changed to UNKNOWN). Two remaining survivors are equivalent mutants: the fee term in the digest (fees are fully determined by fills already hashed, and change equity) and `max()` on the clock (removed: now a backwards step raises).
- **Evidence (local):** SQLite 660 passed / 39 skipped; PG16 663 passed / 36 skipped; ruff real-error check clean. Hosted CI run 42010671559 on `baa120f`: all 9 jobs green.
- **Limits / findings for 3B:** (1) throughput ≈ 55 ms per strategy tick (6 strategies × 220 bars took 73 s), so a year of 5m bars (~105k) would take about 1.5 h per strategy: 3B must measure this and probably cache indicators; (2) strategy parameters can't be overridden yet (BotRunner builds default parameters), which walk-forward/optimisation will need; (3) bar volume/range used for costs is the full bar's, known only after the bar, a modelling approximation; (4) spot long-only, one market order type, no funding.
