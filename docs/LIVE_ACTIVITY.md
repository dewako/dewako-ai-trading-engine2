# Live Activity (Phase 4.4)

A read-only, authenticated view of what the backend actually did. Nothing here is generated by the UI or the AI; every event maps to a stored row.
**Live trading stays LOCKED.** This feature cannot place, retry, cancel or resend an order and cannot change safety state.

## Sources
| Source | Used for |
|---|---|
| `audit_log` (immutable, hash-chained) | startup/shutdown, auth, config, kill switch, risk approval, authorization blocks, package events, AI events |
| `order_events` (joined to orders, intents, signals, strategy_versions) | the order lifecycle (canonical; the audit ORDER_* duplicates are excluded so nothing is double counted; `ORDER_BLOCKED` stays) |
| `reconciliation_events` | reconciliation findings |

No event type exists unless one of these sources produces it.

## Event schema (v1)
`event_id`, `ts` (UTC ISO-8601), `type`, `category`, `severity` (INFO/WARNING/ERROR/CRITICAL), `environment`, `correlation_id`, `strategy`, `strategy_version`,
`strategy_fingerprint`, `instrument`, `adapter`, `related_id`, `summary`, `details` (sanitized, bounded), `status`, `source`, `actor`, `reconciliation_required`.
An order whose outcome is unknown has `status: "UNKNOWN"`, `severity: ERROR`, `reconciliation_required: true` and a summary ending "OUTCOME UNKNOWN, RECONCILIATION REQUIRED". It is never shown as filled or failed.
`details` never carries secrets, file contents or stack traces (redacted and length-bounded).

## Endpoints (permission `read`)
- `GET /activity?limit&cursor&category&severity&status&strategy&environment&instrument&source&correlation_id&type&q&since&until` — newest first, keyset pagination. `limit` ≤ 200. `cursor` is opaque and strictly validated (422 if malformed). A request scans at most 2000 rows.
- `GET /activity/status` — `{level: IDLE|RUNNING|DEGRADED|ERROR, reasons, unresolved_orders, kill_switch, live_trading, ...}` derived from worker health, orders, incidents, audit-chain health and the last start-up. Unknown/reconciling orders force ERROR.
- `GET /activity/stream` — Server-Sent Events. Frames: `hello`, `activity`, `cursor`, `error`, `closed`, comment heartbeats every 15 s.
- `GET /auth/me` — name, role and permission names (the UI uses it only to hide buttons; the server enforces everything).
- `GET /ui` — serves the dashboard same-origin.

## Stream semantics
Resume with `Last-Event-ID` or `?cursor=`. Delivery is **at-least-once**; clients de-duplicate by `event_id`. Authorization is re-checked during the stream; limits: 20 concurrent streams, 600 s per connection (the client reconnects), ≤ 5 consecutive backend errors before closing. Error frames carry a code only.
Each poll batch's cursor is attached only to its final activity frame. If a connection drops before that checkpoint, reconnect may replay events from the incomplete batch; the client must de-duplicate them. A cursor received on the final frame covers every event delivered before that checkpoint.
The browser client uses `fetch` + `ReadableStream` (EventSource cannot send an Authorization header). Reconnect uses capped exponential backoff.

## Dashboard behavior
Sign in on the Live Activity or Strategy Manager page (token in memory only). Filters reload from the server; "Load older events" follows `next_cursor`. The in-browser buffer is bounded (500). **Pause** only holds *display* of new events (held items are bounded at 200 and critical ones are never dropped); the backend and stream keep running, and a banner states how many, and how many critical, are held. UTC/local toggle. States: loading, empty, no-match, disconnected, stale (no data/heartbeat for 45 s), permission denied, backend error. Animations are disabled under `prefers-reduced-motion`; critical/unknown events are visually prominent and never animated away.

## Recovery
Activity is derived from stored rows, so nothing is lost if the stream drops: reconnect (automatic) or "Refresh now". Restarting the backend loses no events.

## Limits and known gaps
- The initial Phase 4.5 implementation report recorded that the routes had not been run on FastAPI over real HTTP. This was subsequently verified in the Windows audit environment with the full backend suite and a real-Uvicorn Chromium run; see `PHASE4_5_INDEPENDENT_AUDIT.md` for current results. CI, PostgreSQL, Docker and real-exchange behavior remain unverified.
- Dashboard policy (Phase 4.5): scripts and styles are external files (`app.js`, `app.css`, `activity.js`, `packages.js`); `script-src 'self'` with **no** `unsafe-inline` and no `unsafe-eval`; verified in Chromium (an injected inline script does not run). One scoped exception remains: `style-src-attr 'unsafe-inline'`, because the prototype builds markup with inline `style="..."` attributes in generated HTML. Style attributes cannot run script; `connect-src`, `img-src` and `font-src` are same-origin, so injected CSS has nowhere to send data. Remaining risk: CSS-based UI redress inside the page if an escaping bug were found; every dynamic value is HTML-escaped (`escapeHtml`) and a hostile file name test passes.
- Web fonts were removed (the CSP blocks third-party hosts); fallback fonts are used.
- `/ui` must be opened as `/ui/` (the server redirects `/ui` to `/ui/`) because the page references its files relatively.
- Pages other than Live Activity and Strategy Manager are **DEMO / SIMULATED** and now say so in a banner on each page; the sidebar no longer shows "Online".
